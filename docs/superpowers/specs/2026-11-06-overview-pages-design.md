# 平台总览与各维度概览（S1.3）设计

> 2026-11-06。对应台账 S1.3（含 D5「平台总览的口径」决策）。
> 用户在 brainstorming 中逐项确认了页面内容；标 **〔实现方决定〕** 的是设计者替用户做的选择，用户可推翻。

## 1. 为什么做

平台总览现在只有集群、租户、命名空间分配三个计数，加一张集群表。各详情页的「概览」页签做得早，
后来上线的应用、中间件、CI、告警都没有进到概览里。用户要的是：**一眼看到常用且重要的资源有多少、
状态如何，以及集群和平台本身是否健康。**

## 2. 目标 / 非目标 / 反目标

**目标**
- 平台总览：全平台合计，只按资源类型展示，不按集群分组。
- 集群、命名空间、节点、租户（平台侧租户详情）四个「概览」页签补上新功能的统计。
- 租户视图的工作台（租户成员看到的总览）与平台总览同形，范围收窄到当前租户。

**非目标**
- 任何 Top N 排行、逐条清单（「需要关注」清单在平台总览上明确不要）。
- 平台总览上按集群拆分。想看单个集群就去集群概览。
- 历史趋势曲线（现有的曲线面板保持不动，不新增）。

**反目标（做了等于失败）**
- 总览信息过多、「看不过来」。用户原话：总览暂时不要展示太多东西。每个区块只给「数量 + 状态拆分」。
- 一个集群连不上就让整页报错或空白。
- 数字悄悄是陈旧的（例如中间件只读入库时的状态，几乎永远是「正常」）。

## 3. 页面内容（用户已确认）

统一形态：**数量卡** = 大号总数 + 一行按状态拆分的小字；**饼图** = 状态分布；**水位** = 进度条（已用 / 上限 + 百分比）。

### 3.1 平台总览（平台视图，管理员）

自上而下：

1. **健康条**（一行）：平台服务正常 x/y；集群 已连接 n · 不可用 m；告警 触发中 k。
2. **数量卡**（一行）：
   - 应用：运行 / 发布中 / 失败 / 下线
   - 中间件实例：正常 / 异常
   - 工作负载：就绪 / 不健康
   - Pod：Running / Pending / 异常
   - 租户：总数（启用 / 停用）、成员数、已分配命名空间数
3. **集群整体水位**：所有**可用**集群合计的 CPU、内存 requests / 可分配，两条进度条。
4. **两个饼图**：
   - 节点：Ready / NotReady；旁边一行整体 CPU、内存 requests 百分比。
   - 命名空间：已分配租户 / 未分配 / 平台系统；旁边一行「配额整体用量 CPU x% · 内存 y%」。
5. 现有的「集群状态表」「快捷操作」「最近访问」保留在下方（不是新增内容，不算「太多」）。〔实现方决定：若视觉上嫌挤，可去掉集群状态表，集群概览页已有〕

不要「需要关注」清单。

### 3.2 集群概览页签

在现有「健康与异常 / 基本信息 / 集群组件」之上加：
- 数量卡：本集群的应用、中间件、CI 流水线、告警（同 3.1 / 3.5 的拆分口径）。
- 两个饼图：节点（Ready / NotReady）、命名空间（已分配 / 未分配 / 平台系统），画法同平台总览。
- 工作负载、Pod 现已在「健康与异常」里，保留。

### 3.3 命名空间概览页签

现在只有基本信息。加：
- 数量卡：工作负载（就绪 / 不健康）、Pod（Running / Pending / 异常）、应用、中间件、CI 流水线、告警。
- 配额水位：CPU、内存的 已用 / 上限 进度条放首屏；没有配额显示「未配置」。（配额与限制范围的详细页签保持不变）

### 3.4 节点概览页签

现在只有基本信息。加：
- 水位：CPU、内存的 requests 与 limits 各占 allocatable 的比例（4 条进度条或 2×2）。
- Pod 数量卡：Running / Pending / 异常（另显示 Pod 数 / podsLimit）。
- 不放应用、中间件等（不按节点划分）。

### 3.5 租户概览（平台侧租户详情里的「概览」页签）

在现有「资源与配额 / 需要关注」之上加：应用、中间件、CI 流水线、告警的数量卡，命名空间数，成员数。
「需要关注」**保留**〔实现方决定：它是租户排查用的，不在用户「去掉」的范围（那句话针对平台总览）〕。

### 3.6 租户视图工作台

与平台总览同形，范围 = 当前租户：应用、中间件、工作负载、Pod、CI、告警数量卡 + 配额水位（CPU / 内存）。
现有「需要关注」「常用操作」「最近访问」保留。不放健康条、节点饼图、命名空间饼图、租户卡（租户看不到这些）。

## 4. 口径

| 项 | 口径 |
|---|---|
| 应用状态 | 读 `platform_application.status`（未删除）：READY=运行；DEPLOYING/DRAFT=发布中〔DRAFT 归「发布中」还是单列「未发布」：实现方决定，倾向单列「未发布」时只在数量>0 时显示〕；FAILED=失败；OFFLINE=下线；DELETING 不计 |
| 中间件状态 | **实时状态**（同中间件列表：按 (code, namespace) 调 k8s-server 评估，`MiddlewareStatusEvaluator`）。READY=正常；DEGRADED/FAILED=异常；CREATING/DELETING 计入总数、拆分里单列「处理中」。**不得只读库里的 status**（入库快照，不回写，会永远显示正常） |
| 工作负载 | 来自集群聚合快照：总数 = deploy+sts+ds；不健康 = `unhealthyWorkloadTotal` |
| Pod | 总数来自聚合；Running / Pending 需**新增按 phase 计数**（聚合现在只有 podCount + 异常数）；「异常」沿用聚合现有定义（abnormalPodTotal，已含 phase=Failed/Unknown 与 CrashLoopBackOff 等）。Pending 的 Pod 同时也算异常时，拆分以「异常」优先、不重复计。phase=Succeeded（Job 跑完）单列「已完成」，**只在数量 > 0 时显示**，保证各档相加 = 总数〔实现方决定〕 |
| CI | 流水线总数 + 每条流水线**最近一次运行**的结果：成功 / 失败（FAILED+TIMEOUT）/ 运行中 / 已取消 / 未运行过 |
| 告警 | 只统计 `status=firing` 的条数，按 severity 拆分（critical / warning / 其它）；不含 Watchdog |
| 节点 | Ready / NotReady 来自聚合 `nodeHealth`；整体 requests 百分比 = Σrequests / Σallocatable |
| 命名空间三类 | **平台系统** = `ProbeNamespaces.DEFAULT` ∪ 平台自身所在命名空间（`platform-system`）∪ `kube-` 前缀；**已分配** = 在 `platform_tenant_namespace`（且不属于平台系统）；**未分配** = 其余。平台系统判定优先 |
| 命名空间配额整体用量 | Σ quota used / Σ quota hard（只算配了 hard 的；全都没配则显示「—」） |
| 集群整体水位 | Σ requests / Σ allocatable，只算可用集群 |
| 平台服务 | platform-api（自身）、platform-auth、platform-gateway、k8s-server 的 actuator health；UP=正常。**分母 = 配了探测地址的服务数**：某服务没配地址（例如某环境没部署网关）就不探测、不计入分母，避免常年显示「3/4」。platform-web 不探测（用户正在看它）〔实现方决定〕 |
| 不可用集群 | 不计入任何合计；健康条显示「不可用 m」并给 tooltip 列名字。整页不因此报错 |
| 空值 | 取不到显示「—」，不显示 0（沿用 B4 口径） |
| 租户 | 总数 / 启用 / 停用来自租户表；成员数 = `platform_user_tenant` 去重用户数（需新 count 查询）；已分配命名空间 = 分配表行数 |

## 5. 已知的数据来源与缺口（调研结论）

已有、可复用：
- 集群聚合快照 `ClusterAggregationOperations` → `/cluster/resource-aggregate`，platform-api 缓存 `cluster:agg:<id>`（TTL 45s）；字段可跨集群求和，租户概览已用 `NamespaceStatMerge` 合并。
- 租户概览 `/tenant/overview`、命名空间切片 `NamespaceStatService`。
- 节点 `GET /nodes/{name}`（capacity/allocatable/podCount/requests）、`/nodes/{name}/pods`。
- 中间件实时状态评估（`MiddlewareService` 列表路径）。

缺口（需要新增）：
1. 聚合里加 **Pod 按 phase 计数**（全局与每命名空间）。
2. 节点 **limits 汇总**（现在只有 requests）。
3. 告警 **firing 计数**（按 cluster / namespace 集合 / severity 聚合），现只有分页列表。
4. CI **每条流水线最近一次运行**的查询（现无）；流水线无 tenant_id，租户范围经分配表 join (cluster_id, namespace)。
5. 应用列表**不能按 namespace 过滤**，计数要直接查库。
6. 成员 **count**。
7. 平台服务健康探测：现无任何汇总，需要 platform-api 去探另外三个服务的 health（地址从现有配置取）。

## 6. 接口形态（建议，细节留给实现方）

- **一个页面一次请求**为原则（与现有总览「首屏只打一次」一致）：
  - `POST /overview/platform` → 平台总览全部数据。
  - 各页签用一个「范围摘要」接口：`POST /overview/scope`，入参 `{scope: CLUSTER|NAMESPACE|TENANT, clusterId?, namespace?, tenantId?}`，返回应用 / 中间件 / CI / 告警四类计数（以及该范围的工作负载、Pod、配额，若页签需要且现有接口不给）。节点页签可直接扩展现有节点详情接口，不必走 scope。
  - 是一个通用 scope 接口还是每页一个接口，**留给实现方**；须遵守「一页一 controller」与「同类资源不抽公共基类」两条既有原则（见 `standing-architecture-principles`）。
- **缓存**：平台总览跨所有集群做聚合 + 中间件实时评估，代价高。复用 `cluster:agg:<id>` 快照；中间件实时状态按集群缓存 45s（同聚合 TTL）。告警 / 应用 / CI 是库查询，不缓存。
- **权限**：
  - 平台总览接口：管理员专属（平台视图本就是管理员专属），新权限行显式绑 `builtin_role_admin`。
  - scope 接口：TENANT/NAMESPACE 范围要校验分配表边界（租户只能查自己分到的命名空间）；租户可读的用 `tenant:` 码并同时绑 admin（见 `permission-multi-code-per-endpoint`）。
  - 本仓无 Flyway：迁移手工重放，部署说明写进台账。
  - 前端按 API 码门控，无权限则跳过该块（沿用 `PlatformOverview` 现有做法），不连弹 403。
  - **逐块按原有读权限过滤**〔实现方决定〕：合并接口拿到 overview 码只代表能打开概览；应用 / 中间件 / CI / 告警
    每一块在后端再按该资源**现有列表接口的读码**判断，没有就返回 `null`（前端不显示该卡），不能因为合并接口
    让没有告警或流水线读权限的成员看到计数。新的 overview 码绑定范围与现有 `tenant:overview:view` 一致
    （平台侧租户概览与租户工作台用同一套规则）。

## 7. 约束

- 前端：Vue 3 + Element Plus；饼图用项目里已有的 echarts（`MetricChart.vue` / `MeshTopologyView.vue` 在用）。
- 后端：k8s-server 零业务逻辑——Pod phase 计数、节点 limits 汇总属于「数据采集」，放在 k8s-core 聚合 / 节点 DTO 里；口径归类（如中间件正常/异常、CI 结果归并）在 platform-api。
- 不加外键；分页走 PageHelper（如需要）。
- 前端收口用 `npm run build`（`vue-tsc --noEmit` 会放过真错误）。

## 8. 留给实现方

- 卡片具体排版、配色、饼图样式（沿用现有 `stat-card` / `panel` 风格）。
- 接口的具体拆分与 DTO 命名（遵守 §6 原则）。
- 平台服务健康探测的超时（建议 ≤2s，并行）与地址来源。
- 分批顺序（建议：①后端缺口 1–7 + 平台总览；②四个概览页签；③租户工作台）。

## 9. 验收

- 平台总览：上述 5 块内容齐全；关掉一个集群（不可用）时页面正常，健康条显示不可用、合计不含它。
- 中间件异常（例如缩容到 0）后 ≤45s 内总览显示为异常。
- 各页签：数字与对应列表页（应用列表、中间件列表、流水线列表、告警列表按同范围筛选）一致。
- 租户成员登录：工作台只含本租户数据；调平台总览接口被拒。
